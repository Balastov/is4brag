# Сценарий приёмки функционала (grounded)

Собирай сценарий приёмки **только** из найденных фрагментов Confluence/KISU
Metro и из явно приложенного пользователем шаблона. Запрещено домысливать
роли, статусы, шаги БП, коды ФТ/доработок и ожидаемые результаты.

## Инструменты

### 1) Сбор источников (обязательно)

```bash
python3 "/app/skills/public/acceptance-scenario/scripts/collect_sources.py" \
  --topic "КРАТКАЯ ТЕМА / КОД (например UTR_01.01.07)" \
  --codes "UTR_01.01.07.01" "ПР_UTR_01.01.07" \
  --json
```

Опционально:

| Параметр | Назначение |
|---|---|
| `--meeting-query "..."` | Доп. поиск по протоколам/встречам |
| `--process-query "..."` | BPMN / Шторм / шаги БП |
| `--template-query "..."` | Поиск шаблона сценария в Confluence |
| `--top-k N` | Чанков на один подзапрос (default 5) |

Скрипт дергает `kisu_metro_search.py` / Search API несколькими запросами и
возвращает JSON с корзинами: `decisions`, `requirements`, `meetings`,
`process`, `template`, плюс `merged` (dedupe по `page_id`+`chunk_id`).

### 2) Шаблон-скелет

Если пользователь не приложил свой шаблон — бери структуру из:

`/app/skills/public/acceptance-scenario/templates/acceptance_scenario.md`

Пользовательский шаблон **важнее** встроенного: сохрани его секции 1:1.

## Алгоритм (3 фазы)

### Phase A — Факты (без сценария)

1. Уточни у пользователя (если не сказано): коды ПР/UTR/FTT/dev, ссылки
   `page_id`, нужен ли фокус на конкретной доработке.
2. Запусти `collect_sources.py` с темой и кодами.
3. При необходимости 1–2 дополнительных поиска через
   `kisu_metro_search.py` по дырам.
4. Составь список **карточек фактов**. Каждая карточка:
   - `fact` — одно атомарное утверждение
   - `page_id`, `title`, `url`
   - `quote` — короткая цитата из чанка (не пересказ «от себя»)
   - `bucket` — decisions | requirements | meetings | process | template | user

Если факта нет в retrieved/вложении пользователя — **не создавай карточку**.

### Phase B — Заполнение шаблона

1. Возьми скелет шаблона (user > built-in).
2. Заполняй слоты **только** из карточек Phase A.
3. У каждого шага/проверки сценария колонка **Источник**:
   `title` + `page_id=<digits>` (и `url`, если есть). Формат `page_id=` обязателен
   для пилотной оценки покрытия.
4. Пустой слот → явно: `НЕ НАЙДЕНО В ИСТОЧНИКАХ` (не выдумывай).

### Phase C — Audit + gaps

В конце ответа обязательные блоки:

1. **Сценарий** (заполненный шаблон).
2. **Пробелы** — список того, чего не хватило (роли, статусы, шаги BPMN,
   ожидаемый результат, данные, права).
3. **Карта источников** — уникальные `page_id` / title / url, реально
   использованные.
4. **Запрещённые домыслы** — если пришлось что-то опустить из‑за отсутствия
   источника, перечисли одной строкой.

## Жёсткие правила

- Нет источника → нет факта в сценарии.
- Транскрипты/протоколы используй как **дельту** (решения, изменения, риски),
  не как замену ПР.
- BPMN/Шторм: только то, что есть в тексте чанков; не восстанавливай схему
  «по логике».
- Не смешивай разные подсистемы/коды без явной связи в источниках.
- Если пользователь дал файлы/фрагменты вне поиска — это bucket `user`, тоже
  с явной пометкой источника «вложение пользователя».

## Пример минимального запуска

Пользователь: «Собери сценарий приёмки по UTR_01.01.07.01 из ПР и протоколов»

1. `collect_sources.py --topic "UTR_01.01.07" --codes "UTR_01.01.07.01" --json`
2. Phase A → факты с page_id
3. Phase B → шаблон
4. Phase C → пробелы + карта источников
